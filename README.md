# DOCX Format Validator

Інструмент для первинної перевірки **оформлення** студентських робіт у форматі `.docx`: поля, шрифт, інтервали, заголовки, зміст, підписи до рисунків і таблиць, посилання на них, формули, додатки, список джерел, посилання `[1]`, нумерація сторінок, типографіка тощо.

Зміст роботи, правильність рішень і плагіат валідатор не перевіряє. Він знаходить формальні порушення й показує, **де саме** їх шукати в документі. Остаточне рішення лишається за викладачем.

Усі документи обробляються локально на вашому комп'ютері й нікуди не надсилаються.

## Для викладачів: швидкий старт

### Варіант 1. Готова програма для Windows (без Python)

1. Завантажте `DocxValidator.exe` зі сторінки **Releases** репозиторію (або з артефактів останньої збірки на вкладці **Actions**).
2. Запустіть файл.
3. Угорі виберіть **профіль вимог**, додайте роботи кнопками **«Додати файли…» / «Додати папку…»** (або перетягніть їх у список) і натисніть **«▶ Перевірити»**.

Якщо кафедра має власний конфіг, покладіть файл `docx_validator_config.yaml` поруч із `DocxValidator.exe`: програма підхопить його під час першого запуску.

### Варіант 2. Через Python (Windows, macOS, Linux)

Потрібен Python 3.10 або новіший.

```bash
pip install -r requirements_docx_validator.txt
python docx_format_validator.py            # без аргументів відкривається вікно програми
```

### Як працювати у вікні програми

| Вкладка | Що там |
| --- | --- |
| **Перевірка** | Список робіт, вибір звітів, запуск. Під таблицею результатів видно зауваження до вибраної роботи з фільтром і пошуком. |
| **Налаштування** | Параметри профілю: поля, шрифт, інтервали, вирівнювання підписів, нумерація сторінок тощо. Галочка «Показати розширені налаштування» відкриває регулярні вирази. Біля кожного виразу є кнопка «Перевірити…», щоб одразу випробувати його на прикладі. |
| **Правила** | Увімкнення й вимкнення цілих груп перевірок і рівень кожного правила: *Помилка / Попередження / Інформація / Вимкнено*. |
| **Довідка** | Коротка інструкція. |

Корисні прийоми:

* **Текст для пошуку** — фрагмент абзацу з проблемою. Подвійний клік копіює його, далі `Ctrl+F` у Word.
* **Правий клік по зауваженню → «Вимкнути правило»** прибирає повідомлення, які заважають саме вам. Щоб зміна збереглася, натисніть «Зберегти» або «Зберегти як…».
* **DOCX з примітками** — копія роботи, де кожне зауваження вставлено як примітку Word у потрібному місці. Її можна одразу надіслати студентові.
* **Зведена таблиця Excel** — підсумок по всіх роботах: скільки помилок і які зауваження трапляються найчастіше.

## Профілі та налаштування

**Профіль** — це набір вимог в одному YAML-файлі з коментарями українською. Той самий файл можна редагувати у вікні програми (вкладки «Налаштування» і «Правила») або вручну в будь-якому текстовому редакторі.

Вбудовані профілі:

| Профіль | Опис |
| --- | --- |
| `coursework` | Курсова робота: поля 2.5/1.5/2/2 см, Times New Roman 14, інтервал 1.5, номер сторінки зверху справа. |
| `iks_coursework` | Курсовий проект з «Інформаційно-комунікаційних систем» за методичкою 2023 р. (Банах, Шабатура): поля зліва 20 мм, решта не менше 10 мм; абзац 1 см; розділи «1 НАЗВА» без слова РОЗДІЛ; АНОТАЦІЯ, ОСНОВНА (ТЕХНІЧНА) ЧАСТИНА, ДОДАТКИ; «Рис. 3.5 — Назва»; джерела в порядку згадки; 35–50 сторінок. |
| `lab_report` | Приклад спрощеного профілю для звіту з лабораторної (без змісту, ВСТУПУ, додатків і нумерації сторінок). Показує, як працює `extends`. |

Як створити власний профіль:

* **У вікні програми:** змініть налаштування → «Зберегти як…» → «Як мій профіль». Профіль з'явиться у списку. Варіант «Як окремий файл» підходить, щоб передати профіль колегам.
* **Вручну:** `python -m lpnu_docx_validator init-config -o мій_профіль.yaml` створює повний файл із коментарями.

Профіль може містити лише відмінності від іншого профілю:

```yaml
extends: coursework        # усе як у курсовій, окрім:
page:
  margin_left_cm: 3.0
  margin_right_cm: 1.0
severities:
  hyphen_instead_of_dash: OFF
```

Помилки в конфігу повідомляються зрозуміло, з номером рядка та підказкою:

```text
Помилки в конфігу мій_профіль.yaml:
  • рядок 2, «body_text.alignment»: «JUSTIFIED» — недопустиме значення; можна: LEFT, CENTER, RIGHT, JUSTIFY, ANY. Можливо, ви мали на увазі «JUSTIFY»?
  • рядок 5, «severities.caption_mising»: невідоме правило. Можливо, ви мали на увазі «caption_missing»?
```

Перевірити файл окремо можна командою `python -m lpnu_docx_validator validate-config мій_профіль.yaml`.

Власні профілі зберігаються в `%APPDATA%\lpnu_docx_validator\profiles` (Windows) або `~/.config/lpnu_docx_validator/profiles` (Linux/macOS). Кнопка «Папка профілів» відкриває цю папку.

## Командний рядок

Старий спосіб запуску працює як і раніше:

```bash
python docx_format_validator.py Course_Petriv.docx -c docx_validator_config.yaml -o Course_Petriv.report.txt
```

Нові можливості:

```bash
# ціла папка: звіти HTML + DOCX з примітками + зведена таблиця
python -m lpnu_docx_validator роботи/ --html --docx -o звіти/ --summary звіти/зведення.xlsx

# вибрати профіль
python -m lpnu_docx_validator робота.docx -p lab_report

python -m lpnu_docx_validator list-rules        # усі правила (докладно: docs/RULES.md)
python -m lpnu_docx_validator list-profiles
python -m lpnu_docx_validator init-config -o мій.yaml
python -m lpnu_docx_validator validate-config мій.yaml
python -m lpnu_docx_validator gui
```

Звідки беруться налаштування: `-c файл` → `-p профіль` → `docx_validator_config.yaml` у поточній папці або поруч із програмою → вбудований профіль `coursework`. Який профіль використано, видно на початку кожного звіту.

Коди завершення: `0` — помилок немає, `1` — знайдено помилки (`ERROR`), `2` — не вдалося виконати (немає файлу, помилка в конфігу).

## Що перевіряється

| Група (`checks.*`) | Що саме |
| --- | --- |
| `page_setup` | Розмір аркуша, орієнтація, поля кожної Word-секції. Альбомні секції для великих таблиць можна дозволити. |
| `page_numbering` | Поле PAGE у колонтитулі: зверху/знизу, вирівнювання (у тому числі через табуляцію чи рамку), старт нумерації зі змісту, прихований номер на першій сторінці. |
| `structure` | Обов'язкові частини і їхній порядок, автоматичний зміст (поле TOC) та його відповідність заголовкам. |
| `paragraph_formatting` | Шрифт, розмір, абзацний відступ, міжрядковий інтервал, інтервали до й після абзацу, вирівнювання. Враховано успадкування стилів, базові стилі, `docDefaults` і шрифти теми. Пункти списків і лістинги коду не плутаються з основним текстом. |
| `empty_paragraphs` | Кілька Enter підряд замість інтервалу чи розриву сторінки. |
| `headings` | Крапка після номера й у кінці заголовка, регістр, напівжирність, вирівнювання (за бажанням), розділ із нової сторінки. |
| `numbering` | Пропуски в нумерації розділів, підрозділів, рисунків і таблиць; номер рисунка, що не відповідає розділу. |
| `captions_and_references` | Підписи рисунків (знизу) і таблиць (зверху), їхнє вирівнювання, дублікати, крапка в кінці, згадка в тексті до появи об'єкта. Розпізнаються діапазони й переліки («рис. 1.1–1.3», «рисунки 2.1 і 2.2»), рисунок із підписом у таблиці без меж і «Продовження таблиці». |
| `section_endings` | Підрозділ без тексту або такий, що закінчується рисунком чи таблицею. |
| `formulas` | Номер формули `(2.1)` і посилання на неї. |
| `tables` | Дозволені розміри шрифту в таблицях. |
| `appendices` | Літери додатків за ДСТУ 3008 (без Ґ, Є, З, І, Ї, Й, О, Ч, Ь), латинська «A» замість «А», послідовність, згадки в тексті. |
| `bibliography` | Наявність списку, нумерація (ручна або автонумерація Word), голі URL, рік, дата звернення, сторінки статей. |
| `source_references` | Посилання `[1]`, `[2–4]`, `[1; 3]`, `[1, с. 25]`; неіснуючі номери, незгадані джерела. Порядок першої згадки — за бажанням. |
| `typography` | Подвійні пробіли, пробіл перед розділовим знаком, дефіс замість тире, прямі лапки, **латинські літери в кириличних словах**, відступ пробілами, Shift+Enter. |
| `document_hygiene` | Невиконані виправлення, примітки, прихований, кольоровий і виділений маркером текст. |
| `images` | Зображення ширші за поле тексту, низька роздільна здатність. |
| `page_count` | Обсяг роботи (вимкнено за замовчуванням; для точного підрахунку потрібен LibreOffice). |

Повний список правил із рівнями за замовчуванням наведено в [docs/RULES.md](docs/RULES.md).

Щоб звіт не тонув в однакових повідомленнях, кожне правило показує не більше 10 повідомлень, решта згортається в рядок «… і ще N». Ліміт змінюється параметром `report.max_per_rule`.

## Що не перевіряється

Зміст і достовірність результатів, академічна доброчесність, читабельність рисунків, повна юридична відповідність бібліографічних описів ДСТУ 8302. Також не перевіряється фактичне розміщення об'єктів на сторінках після верстки: DOCX не зберігає розбивку на сторінки.

DOCX може бути влаштований дуже по-різному: стилі, пряме форматування, автонумерація, таблиці без меж, поля, елементи керування вмістом. Тому валідатор — інструмент первинної перевірки, а не остаточний вердикт.

## Для розробників

```text
lpnu_docx_validator/
├── settings.py        # ЄДИНЕ джерело параметрів і правил: типи, значення за замовчуванням, підписи, YAML
├── docmodel.py        # блоки документа + StyleResolver (успадкування стилів як у Word)
├── checks/            # перевірки за групами: page, structure, text, objects, bibliography
├── report.py          # TXT / HTML / JSON / DOCX з примітками
├── batch.py           # пакетна перевірка, зведена таблиця
├── cli.py             # командний рядок (сумісний зі старим запуском)
├── gui.py, gui_logic.py
└── profiles/          # вбудовані профілі
docx_format_validator.py   # обгортка для старого способу запуску
tests/                     # pytest; документи генеруються кодом (tests/docbuilder.py)
```

Як додати правило:

1. Опишіть його в `RULES` у `settings.py`: id, група, рівень, назва.
2. Викличте `ctx.rep.add("<id>", "повідомлення", block)` у відповідній перевірці. Тест `test_every_rule_used_in_code_exists` стежить, щоб правила в реєстрі й у коді збігалися.
3. Новий параметр додайте в `PARAMS`: він автоматично з'явиться в GUI, конфігу та перевірці конфігу.
4. Перегенеруйте файли:

   ```bash
   python -m lpnu_docx_validator init-config --force -o docx_validator_config.yaml
   python -m lpnu_docx_validator init-config --force -o lpnu_docx_validator/profiles/coursework.yaml
   ```

   і оновіть `docs/RULES.md` (`list-rules --markdown`). Тести перевіряють, що ці файли не застаріли.

Тести й збірка:

```bash
pip install -r requirements_docx_validator.txt pytest ruff
pytest -q && ruff check lpnu_docx_validator tests
```

GitHub Actions проганяє тести на Python 3.10–3.13, відкриває справжнє вікно під xvfb і збирає `DocxValidator.exe` та `docx-validator-cli.exe` для Windows. На тегах `v*` файли публікуються в Releases.
